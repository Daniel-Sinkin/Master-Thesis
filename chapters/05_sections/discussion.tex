\section{Discussion}\label{sec:discussion}

This section combines kernel-level and system-level findings into practical
guidance for the next optimisation cycle.

\subsection{What Improved and Why}

Beyond raw speedup, the key question is which mechanism caused the improvement
(launch reduction, memory locality, occupancy tuning, or precision-path
choice). Profiling evidence is used to support each claim,
using the fixed KPI pack defined in \cref{tab:kpi-pack} so that attributions
remain comparable across kernels and optimisation stages.

\subsection{How Well Results Transfer}

Improvements are classified as:

\begin{itemize}
  \item \textbf{likely to carry over} (expected to transfer across Ampere-like systems),
  \item \textbf{topology dependent} (depends on node NUMA/NVLink structure),
  \item \textbf{workload dependent} (effective only for the studied contraction
    distribution).
\end{itemize}

\subsection{Microbenchmark Implications for Tensor Networks}

The two most useful profiling microbenchmarks are the coalescing sweep
(\cref{tab:coalescing-sweep,fig:phenomena-coalescing}) and the register
pressure study (\cref{tab:register-pressure,fig:phenomena-register-pressure}).

The coalescing sweep shows that going from stride-1 to stride-32 collapses
memory efficiency quickly once warp lanes lose contiguous access. The
practical consequence: layout transforms and contraction orderings that keep
the hottest contracted index unit-stride in memory pay off disproportionately.

The register-pressure experiment shows the flip side: occupancy drops from
$100\%$ to $62.5\%$ and throughput drops with it, so ``more in-register
work'' is not monotonically better. Unroll depth and accumulator count have
to be tuned jointly with occupancy targets, not in isolation.

The irregular training pair in \cref{tab:irregular-training-runtime,tab:irregular-training-kpi}
adds one immediately usable rule for upcoming kernels with skewed shapes
(e.g.\ $47\times84$ blocks): prioritise launch structure and host/device
orchestration before low-level arithmetic tuning. In that run, moving from
serial per-batch launches to one batched launch per step gave a
$71.7\times$ step-time reduction while K10 stayed nearly unchanged, which
indicates that scheduler feed and launch/copy structure, not divergence,
dominated performance.
