\section{Occupancy and Launch Configuration}\label{sec:occupancy}

Launch configuration is a constrained resource-allocation problem on each SM.
Using more registers or shared memory per thread can speed up the inner loop
but cuts occupancy, which in turn hurts latency hiding.

\subsection{Tuning Procedure}

The tuning sequence is:

\begin{enumerate}
  \item choose an initial block size (typically 128 or 256 threads),
  \item inspect register use and shared-memory use per block,
  \item estimate achievable occupancy,
  \item benchmark and profile stall reasons,
  \item retune block size and launch bounds based on measured bottlenecks.
\end{enumerate}

If memory stalls dominate, higher occupancy is often preferred. If execution is
compute-bound with low dependency stalls, lower occupancy with higher
per-thread work can be superior.

\subsection{Worked Occupancy Example on A100}
\label{sec:occupancy-worked-example}

The two occupancy schematics in \cref{fig:occupancy-visual-example} use one SM
with the following capacity model:
\num{2048} threads, \num{65536} registers, and \SI{160}{\kilo\byte} shared
memory. This is the same setup used in the diagrams for visual clarity.

Initial kernel setup:
\begin{align}
  b &= 256 \text{ threads per block}, \\
  r_t &= 64 \text{ registers per thread}, \\
  s_b &= \SI{48}{\kilo\byte} \text{ shared memory per block}.
\end{align}

Per-block resource use:
\begin{align}
  r_b &= b \cdot r_t = 256 \cdot 64 = 16384 \text{ registers}.
\end{align}

This corresponds to:
\begin{itemize}
  \item thread share per block: $256/2048 = 12.5\%$,
  \item register share per block: $16384/65536 = 25\%$,
  \item shared-memory share per block: $48/160 = 30\%$.
\end{itemize}

The block residency limits are (thread limit $N_t$, register limit $N_r$,
shared-memory limit $N_s$):
\begin{align}
  N_t &= \left\lfloor \frac{2048}{256} \right\rfloor = 8, \\
  N_r &= \left\lfloor \frac{65536}{16384} \right\rfloor = 4, \\
  N_s &= \left\lfloor \frac{160}{48} \right\rfloor = 3.
\end{align}
Therefore
\begin{align}
  N_{\text{res}} = \min(N_t,N_r,N_s)=\min(8,4,3)=3,
\end{align}
so this case is \textbf{shared-memory occupancy limited}
(\cref{fig:occupancy-sm-limited}).

After reducing shared memory to
\begin{align}
  s_b = \SI{32}{\kilo\byte},
\end{align}
the shared-memory limit becomes
\begin{align}
  N_s = \left\lfloor \frac{160}{32} \right\rfloor = 5.
\end{align}
Now
\begin{align}
  N_{\text{res}} = \min(N_t,N_r,N_s)=\min(8,4,5)=4,
\end{align}
so the limiting resource changes to \textbf{registers}
(\cref{fig:occupancy-reg-limited}).

In this transition, resident threads increase from
$3\cdot256=768$ to $4\cdot256=1024$, i.e.\ from \SI{37.5}{\percent} to
\SI{50}{\percent} of the SM thread capacity.

\subsection{Launch Overhead Considerations}

For small kernels, launch latency can dominate irrespective of occupancy.
Therefore occupancy tuning is combined with launch reduction techniques (kernel
fusion or persistent execution) rather than treated in isolation.
